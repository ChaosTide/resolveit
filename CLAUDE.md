## Project

ResolveIT (CTS 4911 capstone): a PHP 8.3 + Microsoft SQL Server IT help-desk ticketing app. Plain PHP,
no framework, no Composer/npm — every page in `public/` is a PHP file that outputs HTML directly. See
[README.md](README.md) for the full feature list and [docs/TECH-STACK.md](docs/TECH-STACK.md) for a
language-by-language breakdown.

## Architecture

**Request flow:** every page in `public/` starts with `require __DIR__ . '/../app/bootstrap.php'`, which
loads config, then `http.php` → `db.php` → `validation.php` → `auth.php` → `workflow.php` → `audit.php` →
`reports.php` → `tickets.php` → `ui.php` (in that order — later ones assume earlier ones are loaded),
starts the session, and re-checks the session's user against the DB on every request (so a role change or
deactivation by an admin takes effect immediately, not just on next login).

**Three environments, selected by `APP_ENV`** (branches in `app/bootstrap.php`):
- unset (this PC): `app/config.php` (gitignored, never committed — copy from `app/config.example.php`),
  Windows Authentication to `WORKSTATION\JLB282`, no password in config.
- `docker`: `app/config.azure.php`, credentials from environment variables (`deploy/docker/.env`,
  generated by `start-docker.ps1` on first run), normal password sign-in.
- `azure`: same config file, but identity comes from Microsoft sign-in via `app/azure-auth.php`
  (`azure_team_identity()` / `azure_team_login()`) instead of a password form.

**`app/` is shared logic, never web-reachable** (kept outside Apache's document root, which points at
`public/` only): `http.php` has `e()`/`redirect()`/`flash()`/CSRF; `auth.php` has login, lockout, and
`require_role()`; `workflow.php` enforces the ticket status machine server-side (Open → Assigned →
In Progress → Resolved → Closed, one step at a time, Resolved may reopen to In Progress, Closed is
final) so tampering with the form can't skip a step; `ui.php` has the shared table/badge/icon builders
used across multiple `public/` pages — check there before writing a new one.

**Styling is one file, token-driven:** all CSS is in `public/assets/style.css`, no framework. Colors,
radii, and shadows are CSS custom properties in the `:root` block — a "change X everywhere" request is
almost always a one-to-two-line edit there, not a per-selector hunt. A few components intentionally keep
a hardcoded light background (inputs, `.chip`, `.button.secondary`) and use `--text-on-light` instead of
the normal `--text` token so their text stays legible against that fixed background.

Static asset links are cache-busted with `?v=<?= filemtime(...) ?>` in `public/partials/header.php`. If
a change looks like it didn't take effect, suspect a stale browser tab/cache before suspecting the server.

**Security model:** password hashes only (`password_hash`/`password_verify`), prepared statements for
every query, CSRF token checked by `verify_csrf()` on every POST, output escaped through `e()`, role
checks via `require_role()` on every page, lockout after 5 failed sign-ins for one email (20 for one IP)
within 15 minutes. Full threat-model writeup and the one real bug found (a login CSRF empty-token gap,
fixed in `1f56f6f`) are in [docs/THREAT-MODEL.md](docs/THREAT-MODEL.md).

**Database:** SQL Server, 12 tables / 14 foreign keys, defined in `database/schema.sql` plus
`database/migrations/001`–`006`. Core tables: `users`/`roles`/`organizations`, `tickets`, the fixed
reference lists `statuses`/`priorities`/`categories` (priorities carry the SLA-hours target), and the
append-only `ticket_notes`/`ticket_history`/`admin_audit_log`/`login_attempts`.
